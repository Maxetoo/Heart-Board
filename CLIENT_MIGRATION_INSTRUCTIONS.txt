0. READ THIS FIRST — WHAT THIS MIGRATION ACTUALLY IS
--------------------------------------------------------------------------------

This is NOT a "swap one folder for another" job. Be clear-eyed about it:

  * `frontend/` is a FULLY INTEGRATED application. It has 8 Redux slices with
    ~45 async thunks covering every backend endpoint, real cookie auth, a
    profile-setup gate, 16 routes, and a working production build that `app.js`
    already serves.

  * `client/` is a DESIGN PROTOTYPE exported from Google AI Studio. It makes
    ZERO network calls to your backend. Verified: the only `fetch()` in the
    whole codebase is `fetch(dataUrl)` in ShareProfileModal.tsx:414 (a blob
    conversion). There is no axios, no API base URL, no auth token handling.

  * All `client/` data is hard-coded: `INITIAL_MOCK_POSTS` (App.tsx:51) and
    `MOCK_REGISTERED_USERS` (types.ts:32). "Login" in AuthModal.tsx:179 does
    `MOCK_REGISTERED_USERS.find(...) || MOCK_REGISTERED_USERS[2]` — it always
    "succeeds" and falls back to Micky Mouse.

So the real work is: KEEP the `client/` UI, and REBUILD into it the entire
integration layer that already exists in `frontend/src/slices/`.

Rough effort split:
    5%   folder/build/deploy rewiring        (Phases 1-3)
   15%   API client + type adapters           (Phases 4-5)
   45%   screen-by-screen data wiring         (Phase 7)
   20%   auth + profile-setup flow            (Phase 6)
   15%   backend gaps + bug fixes + QA        (Phases 8-10)

DO NOT delete `frontend/` until Phase 12. It is your only working reference for
how every endpoint is called, and your rollback path.

2. DECISIONS TO MAKE BEFORE YOU TOUCH CODE
--------------------------------------------------------------------------------

D1. FOLDER NAME
    Option A (RECOMMENDED): keep the new app at `client/`, retire `frontend/`
        to `legacy-frontend/`, and update the 3 backend references.
        + No huge rename diff, `client/` is the more conventional name.
        - Must edit app.js and package.json (2 small edits).
    Option B: `git mv frontend legacy-frontend && git mv client frontend`
        + Zero backend edits.
        - Every deploy config / doc / muscle memory that says "frontend" now
          points at the new app; harder to tell the two apart in history.
    This document assumes OPTION A. If you take B, invert the paths in Phase 1.

D2. STATE MANAGEMENT
    Option A (RECOMMENDED): thin service modules + React Context + local state.
        The `client/` code is already 100% component-state driven. Porting Redux
        would mean rewriting App.tsx's 30+ useState hooks. Instead add
        `client/lib/api.ts` + `client/services/*.ts` and an AuthContext.
    Option B: port the 8 Redux slices from `frontend/src/slices/` to TS.
        Only worth it if you want the exact same loading/error flags.
    Option C: TanStack Query on top of the service modules. Best long-term for
        the feed/pagination/caching, but it's a new dependency and a new mental
        model. Fine to adopt in Phase 7 for the feed only.

D3. TAILWIND
    Option A (RECOMMENDED): install Tailwind properly as a PostCSS build step.
        The Play CDN prints a console warning, blocks first paint, cannot be
        cached, and will not work offline. There are ~1,342 className usages —
        they all keep working after a proper install.
    Option B: ship the CDN. Acceptable ONLY for an internal demo. Do not ship
        it to production.

D4. FLAT LAYOUT vs src/
    Option A (RECOMMENDED): move client's app files into `client/src/`.
        Matches the old app, keeps `client/` root for config, and prevents
        `dist/`, `node_modules/`, `App.tsx` all living side by side.
        Requires updating index.html's script src and the `@` alias.
    Option B: keep it flat. Works, but the root gets noisy fast once you add
        lib/, services/, contexts/, types/, assets/.

D5. SCOPE OF THE FIRST CUTOVER
    Option A (RECOMMENDED): ship a "vertical slice" first — auth + feed +
        board detail + create board — behind the real API, and keep mock data
        for hearts/contributions until Phase 8 backend work lands.
    Option B: big-bang cutover. Higher risk; you'll be debugging auth,
        pagination and the canvas editor simultaneously.

6. PHASE 3 — ROUTING (blocking; do before any data wiring)
--------------------------------------------------------------------------------

This phase is non-negotiable. The backend and your emails generate PATH URLs,
and the new client uses a HashRouter with two routes.

6.1 SWITCH HashRouter -> BrowserRouter.
    `client/src/App.tsx:3`:
        import { HashRouter as Router, Routes, Route } from 'react-router-dom';
        =>
        import { BrowserRouter as Router, Routes, Route } from 'react-router-dom';

    WHY THIS IS MANDATORY:
      - `app.js` already serves index.html for every non-/api path, so
        BrowserRouter works with zero server changes.
      - `controllers/authController.js` redirects Google OAuth back into the SPA
        — a path, not a hash.

        DONE (2026-09-06): those redirects used `CLIENT_URL`, which in this
        checkout points at the API tunnel rather than the app. A successful
        Google sign-in therefore landed the browser on the API host. They now
        use `configs/origins.js -> appUrl()`, derived from ALLOWED_ORIGIN, which
        is also the list CORS uses — one source of truth for "where the browser
        app lives".

        ENV RULE: ALLOWED_ORIGIN must be the origin the SPA is served from
        (it may be a comma-separated list; the first entry is canonical).
        CLIENT_URL is now only a fallback. If you move the SPA behind a tunnel
        or a new domain, update ALLOWED_ORIGIN — not CLIENT_URL.
      - Email verification / password reset links carry `?verificationToken=` and
        `?token=` query params on paths. With HashRouter the router never sees
        them at the right place.
      - `boardController.shareBoard` returns a `shareUrl` for a board slug.
        Shared links must be `/board/:slug`, not `/#/board/:slug`.

        export const API_ORIGIN =
          import.meta.env.VITE_ORIGIN_URL || 'http://localhost:8080';

        export const api = axios.create({
          baseURL: `${API_ORIGIN}/api/v1`,
          withCredentials: true,               // REQUIRED: signed cookie auth
          headers: { 'Content-Type': 'application/json' },
        });

        // Normalise the backend's inconsistent error shape.
        // Controllers return { message } in most places but { msg } in
        // logout/errorMiddleware. Handle BOTH.
        export type ApiError = { status: number; message: string };

        export function toApiError(e: unknown): ApiError {
          const err = e as any;
          return {
            status: err?.response?.status ?? 0,
            message:
              err?.response?.data?.message ??
              err?.response?.data?.msg ??
              err?.message ??
              'Network error occurred',
          };
        }

        api.interceptors.response.use(
          (r) => r,
          (error) => {
            if (error?.response?.status === 401) {
              // cookie expired or missing -> clear local user, prompt auth
              window.dispatchEvent(new CustomEvent('heartboard:unauthorized'));
            }
            return Promise.reject(error);
          },
        );

     boardController.getMyBoards.
     MEDIUM-HIGH effort. Decide early — it changes the permission model.

11.3 HEART TOKENS ("gift a heart", heart_token post type, selectedHearts,
     heartDetails{id,label,emoji,bubbleColor}, heartsCount, 'hearts' profile
     tab, heartFilter received|sent, HeroHeartAnimation, LiveHeartAnimation)
     This is a whole product feature with zero backend. The closest existing
     thing is `user.stats.profileLikes` (a single integer) and BoardLike's
     reaction enum.
     FIX: new `HeartToken` model { from, to, type/label, emoji, color, message,
     createdAt } + endpoints POST /heart, GET /heart?direction=sent|received.
     HIGH effort. Strong candidate to CUT from the first cutover — keep the
     animations as decoration and hide the gifting CTA until the model exists.

11.4 PER-TYPE REACTION COUNTS (reactionCounts{clap,heart,smiley,fire},
     userReactions[], onUpdateReactions, onReactionBlown)
     Backend BoardLike enforces ONE reaction per user per board
     (`LikeSchema.index({board:1,user:1},{unique:true})`) with the enum
     ['clap','heart','thumbs','smile','fire']. The client wants MULTIPLE
     reactions per user AND per-type totals. Also note the name mismatch:
     client 'smiley' vs backend 'smile', and the backend has 'thumbs' which the
     client doesn't offer.
     FIX (minimum): align the enum names, and aggregate counts per reaction in
     boardController (a $group on BoardLike) returned with the board.
     FIX (full): drop the unique index, allow one row per (board,user,reaction).
     MEDIUM effort. At minimum, fix the enum mismatch before launch or reactions
     will silently 400.

11.5 USER BIO + VERIFIED BADGE (bio, isVerified)
     Neither exists on UserSchema. The design shows both prominently on every
     profile and post card.
     FIX: add `bio: {type:String, maxLength:160}` and
     `isVerified: {type:Boolean, default:false}` to UserSchema; expose bio in
     PATCH /user/profile's allowed fields (userController.updateProfile
     currently destructures only {username, profileImage, country, accountType}).
     LOW effort. Do this one.

11.6 SEARCH
     No public search endpoint. See 10.8.
     FIX: GET /api/v1/search?q=&type=all|users|boards|hashtags returning
     { users, boards, hashtags }. Text-index `username` on User and
     `title description tags` on Board. MEDIUM effort.

11.7 GLOBAL REALTIME STATS (App.tsx realtimeStats)
     FIX: GET /api/v1/stats -> { totalMessages, totalCurators, totalReactions },
     cached in Redis for 60s (cacheMiddleware already exists for this).
     LOW effort.

11.8 SEPARATE DISPLAY NAME
     The client shows `name` ("Cristiano Ronaldo") and `handle` ("@cristiano")
     as distinct values. The backend has ONE `username` field, 3-14 chars.
     Every profile in the design breaks this.
     FIX: add `displayName: {type:String, maxLength:50}` to UserSchema, or
     accept that name === username everywhere and update the designs.
     LOW effort, but it affects every screen — decide before you build adapters.

11.9 GUEST CONTRIBUTIONS — see 9.5.

11.10 DIRECT / WALL MESSAGES
     postDirectMessage and getUserWallMessages exist server-side but are
     currently UNREACHABLE (see 12.2). The client's "send message to user" flow

12. PHASE 9 — EXISTING BACKEND BUGS TO FIX DURING THE MIGRATION
--------------------------------------------------------------------------------

Found while auditing. Fix these while you're in here; the new client will hit
all of them.

12.1 UNREACHABLE ROUTE — POST /message/:username  (routes/messageRoute.js)
     `MessageRoute.post('/:slug', ...postMessage)` is registered BEFORE
     `MessageRoute.post('/:username', ...postDirectMessage)`. Express matches
     in order, and both are single-segment patterns, so `/:slug` always wins.
     postDirectMessage is DEAD CODE — direct/wall messages cannot be created.
     FIX: give them distinct prefixes, e.g.
         POST /message/board/:slug     -> postMessage
         POST /message/direct/:username -> postDirectMessage

12.2 UNREACHABLE ROUTE — GET /message/:username  (same file)
     `MessageRoute.get('/:id', ...getMessage)` shadows
     `MessageRoute.get('/:username', ...getUserWallMessages)` for the same
     reason. getUserWallMessages is DEAD CODE.
     FIX: GET /message/wall/:username.

12.3 CLIENT/SERVER URL MISMATCH — moderateBoardMessage
     legacy-frontend/src/slices/messageSlice.js calls
         PATCH /api/v1/message/board/${id}/moderate
     but routes/messageRoute.js defines
         PATCH /api/v1/message/:id/board/moderate
     These do not match — the call 404s today. Pick one (the route's shape is
     odd; `PATCH /message/:id/moderate?context=board` would be cleaner) and make
     the new client match it.

12.4 SPELLING — `receipent` (should be "recipient") appears in BoardSchema as
     `receipent`, `receipentOriginal`, `receipentHashtag`, `receipentFlagged`,
     and — differently misspelled — `receiprentFlagReason`. The client uses
     `recipientName` / `recipientHandle`.
     You have two choices, and BOTH are fine, but choose deliberately:
       (a) Leave the DB alone; absorb the spelling in the adapter layer only.
           Zero migration risk. RECOMMENDED for this cutover.
       (b) Rename the schema fields + write a MongoDB migration script.
           Cleaner long-term; do it as a separate, isolated change AFTER the
           frontend cutover is stable. Never bundle a data migration with a
           frontend migration.

12.5 REDIS CACHE MIDDLEWARE — `middlewares/cacheMiddleware.js` opens with a
     large commented-out block. Confirm which implementation is actually
     exported and live. If caching IS live, note that board/message caches are
     invalidated inside controllers; any new endpoint you add (stats, search,
     hearts) needs matching invalidation or you will serve stale data.

12.6 RATE LIMIT — global 100 requests / 15 min / IP (app.js). The new client is
     much chattier than the old one (feed + profile + reactions + moderation).
     A single active session can exhaust that. Raise it, or scope it: keep a
     tight limit on /auth/* and /ai/*, and a looser one on GETs.

12.7 CORS — `origin: [origin, 'https://res.cloudinary.com']` where
     `origin = process.env.ALLOWED_ORIGIN` (a single value). If you serve the
     SPA from the same Express app this is moot, but the dev setup
     (client:3000 -> api:8080) needs http://localhost:3000 in the list, or use
     the Vite proxy from 7.4 and sidestep CORS entirely. RECOMMENDED: the proxy.

12.8 Two Mongo connections are opened in app.js (a raw MongoClient AND
     mongoose). The MongoClient is only used for a ping. Harmless but wasteful —
     drop it while you're cleaning up.
